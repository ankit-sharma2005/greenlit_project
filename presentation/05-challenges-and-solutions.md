# Challenges and solutions

Use these stories to explain engineering decisions. Each distinction between implementation, mocked testing, and live verification is intentional.

| Challenge | What happened | Root cause | How it was solved or contained | What I learned | Evidence |
|---|---|---|---|---|---|
| Free-tier provider quotas | A provider can limit requests by minute, day, or token size. Runs must not turn a quota limit into a misleading success. | External providers impose limits, and this repo's limiter state is held in process memory. | `ProviderRateLimiter` serializes provider requests, tracks RPM/RPD, and raises a pause condition at the daily quota. The gateway can move to configured fallbacks for retryable provider failures. Run processing pauses on daily quota. This is not distributed: limits are neither shared across API processes nor persisted after restart. Real provider quota behavior was not tested with credentials. | Separate “wait in line” limits from “daily quota exhausted,” and make the latter visible/recoverable. Do not promise a cross-process quota guarantee from an in-memory counter. | `backend/app/services/rate_limit.py`; `backend/app/services/llm_gateway.py`; `backend/app/services/run_engine.py`; `test_provider_rate_limiter_queues_rpm_and_pauses_at_rpd`; `docs/PROGRESS.md` Phase 2. |
| Runs that survive interrupted work | A run has to track per-item state so one bad item does not erase progress. | A single long synchronous request is fragile and cannot give resumable per-item status. | Celery and Redis separate work from the API. `EvalRun`/`EvalRunItem` persist status and counts; the worker loops through pending/running items, handles item exceptions, and pauses on quota. Cancel/pause/resume and recovery logic have tests; the worker-kill/restart check is still marked manual in the progress log. | Persist the unit of work and make the recovery boundary explicit. A tested recovery path is not the same as observing a real worker crash/restart. | `backend/app/services/run_engine.py`; `backend/app/worker.py`; `backend/app/routers/phase3.py`; `backend/tests/test_phase3.py`; `docs/PROGRESS.md` Phase 3. |
| Unreliable or malformed LLM judge output | A judge can produce invalid JSON or react to hostile instructions embedded in the evaluated text. | Generative output is not inherently schema-valid, and user-provided evaluation text is untrusted input. | The judge result is validated with a Pydantic model, malformed output is retried once, and cache identity includes rubric/provider/model/input. Prompts delimit untrusted evaluation data and instruct the judge not to follow it. The prompt-injection test uses a mocked provider; it is not evidence that every live model resists injection. | Validate model output as input, record the rubric/model provenance, and test both good and malformed responses. | `backend/app/services/metrics.py`; `backend/app/models.py` (`JudgeMetricCache`); `test_malformed_judge_json_is_retried_and_validated`; `test_judge_cache_avoids_second_provider_call`; `test_judge_prompt_treats_hostile_answer_as_untrusted`; `docs/PROGRESS.md` Phase 4. |
| Safely connecting arbitrary applications | A connector may send requests to arbitrary URLs or start commands. Unsafe execution could expose local services, credentials, or the host. | User-controlled URLs and code cross a trust boundary. A real sandbox needs isolation, resource caps, and network policy; merely launching a process is not enough. | Connector code checks outbound targets and keeps unsupported connector types gated. Python Function and Python SDK Traced are disabled rather than executing arbitrary user code without an isolated runner. Docker/Git/CLI/Proxy/Website/MCP are marked unavailable pending verified runtime conditions. Do not describe sandboxing as completed. | Prefer an honest rejection over a fake trace or a false security boundary. Prove isolation with runtime tests before enabling a connector. | `backend/app/services/connectors.py` (`_check_target_is_public`, `validate_connector_settings`); `backend/app/phase2_schemas.py`; `frontend/src/WorkspaceProjects.tsx`; `test_registry_lists_all_thirteen_types_and_validates_type_settings`; `docs/AUDIT.md` Known limitations. |
| One trace contract for different app visibility | Some apps reveal only inputs and outputs; others may expose retrieval, tool, or model details. | Different integrations have different observability. A metric cannot calculate a component score if the connector never supplied the component data. | Connector responses use a normalized output/steps/usage/latency/model shape. Metric definitions list required fields; absent instrumentation is reported as `not_instrumented`, not treated as a bad score. Python SDK tracing remains disabled. | Keep the minimum contract small; make optional instrumentation explicit instead of inventing missing values. | `backend/app/services/connectors.py` (`_trace_response`); `backend/app/services/metrics.py`; `backend/app/tracing.py`; `test_missing_required_metric_fields_are_not_instrumented`; `docs/PROGRESS.md` Phases 2 and 4. |
| Authentication and workspace boundaries | Tokens, credentials, and data must be separated between workspace users. | A shared system needs session lifecycle, per-role access, and workspace-scoped lookups. | Passwords use Argon2 via Passlib; refresh tokens are held in httpOnly cookies and rotated; reset and API tokens are stored hashed; provider/connector secrets use Fernet encryption; role dependencies and workspace filters guard routes. Tests cover refresh/logout, reset invalidation, Viewer restrictions, workspace isolation, and secret redaction. | Authentication is more than issuing a JWT: token rotation, role checks, scoping, storage, and audit evidence all matter. | `backend/app/security.py`; `backend/app/routers/auth.py`; `backend/app/deps.py`; `backend/app/services/secrets.py`; `test_login_refresh_and_logout_flow`; `test_password_reset_uses_one_time_token_and_revokes_sessions`; `test_viewer_and_cross_workspace_access_are_forbidden`. |
| Keeping judge scores interpretable | A numeric score by itself does not explain whether it is trustworthy or comparable. | Different judge models and rubrics may yield different judgments; free or weaker models may vary. | Judge profiles carry role, model, and rubric version; metrics preserve score provenance; Phase 8 implements calibration calculations such as Cohen's kappa, Krippendorff's alpha, Spearman correlation, and confusion matrices. No actual human-labeled calibration study or reliability threshold is established in the repository. | Calibration tooling enables a study; it does not prove a judge is calibrated until real human labels and representative data are collected. | `backend/app/models.py` (`JudgeProfile`); `backend/app/services/human_review.py`; `test_calibration_summary_reports_kappa_alpha_and_confusion_data`; `docs/PROGRESS.md` Phase 8. |
| Avoiding stale-baseline comparisons | A version change should be measured against the same examples and paired item identities. | Comparing unrelated datasets makes score deltas hard to interpret. | The comparison endpoint rejects runs with different dataset versions or splits. Paired statistics and critical-item tracking feed regression PASS/WARN/BLOCK. | Hold the test set constant when claiming a version improved or regressed. | `backend/app/routers/phase6.py` (`_validate_comparable_runs`); `backend/app/services/comparison.py`; `backend/app/services/statistics.py`; `test_seeded_regressing_version_returns_block_with_new_failure`. |
| Demo data versus a working seeded environment | Phase 9 labels GOOD, BROKEN, and REGRESSING as seed states. | The current `scripts/seed_demo.py` builds a small static mapping and writes JSON; it does not create database users, a demo project, a live RAG app, or the seeded website specified in the project spec. | The limitation is called out instead of presenting the JSON export as a running demo environment. The states are useful as illustrative examples and export inputs only. | A “seed” command should be described by its side effects, not by its name. Static examples are not integration-test fixtures or live accounts. | `scripts/seed_demo.py` (`build_demo_states`, `main`); `backend/tests/test_phase9_seed.py`; `docs/PROGRESS.md` Phase 9; `docs/AUDIT.md`. |
| Documentation and tests drifting apart | Some tests still expect old successful connector behavior while current registry metadata gates those types. | Product status and older test assertions were updated at different times. | The audit and progress docs record limitations; latest test failures are reported as failures, not suppressed. The proxy request-template parser received a targeted fix and test history. | Documentation is useful only when it agrees with current code and test behavior. Re-run acceptance checks after behavior changes. | Commit `20f8631` (“Fix proxy connector template parsing”); `backend/app/services/connectors.py`; `backend/tests/test_phase2.py`; `backend/tests/test_phase10.py`; latest suite result in [06-results-and-limitations.md](06-results-and-limitations.md). |
| Phase gates for AI-assisted development | The repository requires phase checklists, validation summaries, known gaps, and a stop-and-wait protocol. | The spec explicitly treats phase acceptance as an evidence-based gate; unverified completion claims risk skipping acceptance work. | `docs/PROJECT_SPEC.md` section 17 defines the protocol; `docs/PROGRESS.md` records phase evidence and limitations; `docs/AUDIT.md` independently summarizes implementation status. The tracked file list does not contain `.github/copilot-instructions.md`. | Keep durable decisions and evidence in the repository so work can be resumed without relying on conversational context. | `docs/PROJECT_SPEC.md` section 17; `docs/PROGRESS.md`; `docs/AUDIT.md`; Git history. |

## Requested stories that the repository does not verify

Do not present the following as documented historical events. The current repo can support a discussion of the environment or a developer's personal recollection, but it cannot verify the details:

- Docker Desktop installation, enabling WSL 2 or Virtual Machine Platform, or which Windows troubleshooting steps were needed. The repo records a working Compose configuration and past healthy status, not those setup steps or versions.
- Copilot stalls, account changes, context-window problems, or exact skipped steps. The repo has a phase protocol and evidence logs, but no tracked Copilot instruction file or incident timeline.
- Running two independent GreenLit projects on one computer without port, Docker, or virtual-environment conflicts. The Compose file uses fixed local ports and documents one stack; a multi-project isolation procedure is not present.
- A real GitHub Models free-tier rate-limit incident or an observed fallback to Ollama. Rate-limiting/fallback code and mocked tests exist, but no live provider credentials or event trace is recorded.

These boundaries make the presentation stronger: distinguish source-backed engineering decisions from personal experience and from runtime evidence.
